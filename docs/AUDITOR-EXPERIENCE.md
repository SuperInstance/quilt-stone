*Status: field report from the STONE-V2-PILOTS first sign pilot (Task 26-d input).
Every command below was executed for real on 2026-09-27 against the merged
sign lane (`signTip`/`verifyTipSignature`, quilt-stone#4, merge `023edbed`)

## The artifact under audit

`checkpoints/stone-v1.signed.json` from a `node tools/prerun.js` run with
`QUILT_STONE_DIR=<quilt-stone checkout>` and `QUILT_STONE_SIGN_KEY=<producer PEM>`.
Shape: a wrapper object

```json
{ "tool": "pong-quilt", "round": "R39", "source": "...",
  "key": { "ephemeral": false, "public": "-----BEGIN PUBLIC KEY-----\n..." },
  "verify": { "ok": true, "tip": "ffe8abd8...", "signer": {...} },
  "chain": [ ...rows..., { "kind": "stone.sign", ... } ] }
```

Audit facts an auditor must confirm before trusting anything inside the
wrapper: the wrapper's `verify.ok` is the *producer's* self-report and is
worthless to the auditor. Only `chain` + `key.public` are inputs.

## The walk (5 checks, each observed)

```js
// auditor.mjs — zero dependencies beyond a quilt-stone checkout
import { verifyChain, verifyTipSignature } from '<quilt-stone>/stone.mjs';
import { readFileSync } from 'node:fs';
const art = JSON.parse(readFileSync('checkpoints/stone-v1.signed.json', 'utf8'));
const rows = art.chain;
const pub = art.key.public;
```

**1. Chain integrity with the staple attached.** The `stone.sign` row is an
annotation — self-hashed against the tip, but `prev` never advances
(STONE-SPEC §4.6.1), so body verification must still pass untouched:

```
verifyChain(rows) -> {"ok":true,"alg":"stone-v1","genesis":"STONE-GENESIS-1",
  "links":6,"tip":"ffe8abd842162d717ff274fdd3c21c58622df9ede534f6b540f2ae16b69f5503", ...}
```

**2. Signature verifies against the embedded public key.**

```
verifyTipSignature(rows, pub) -> {"ok":true,"tip":"ffe8abd8...",
  "signer":{"alg":"ed25519","key_id":"pq-prerun-sign-pilot","signer_role":"producer"}}
```

**3. Negative control — body tamper.** Flip one payload byte (an `md5` field)
without touching any `row_hash`:

```
verifyChain(tampered) -> {"ok":false,"why":"hash mismatch"}
```

The hash chain catches content edits. This is necessary but NOT sufficient —
a forger with the dialect spec can re-seal and get green hashes. That is what
the staple is for.

**4. Negative control — the laundering attempt.** Tamper a body row, re-seal
with `sealChain` so every hash is green again, then copy the original
`stone.sign` row verbatim onto the forged chain. Observed:

```
verifyChain(forged)            -> {"ok":false,"why":"hash mismatch"}
verifyTipSignature(forged,pub) -> {"ok":false,"why":"signed tip does not match the chain tip (post-signature chain edit)"}
```

Both gates refuse; the signature gate names the exact reason. The signed
message is `"stone-v2" || tip_row_hash` (pinned byte-level in the sign lane's
smoke), so a re-sealed chain has a different tip and the copied staple
cannot transfer.

**5. Negative control — wrong key.** A fresh ed25519 keypair must refuse:

```
verifyTipSignature(rows, otherPub) -> {"ok":false,"why":"signature invalid for this tip and key"}
```

## Auditor experience notes (the 26-d payload)

1. **The wrapper is not evidence.** The producer self-reports `verify.ok` at
   birth; the auditor re-runs checks 1–2 from `chain` + `key.public` alone.
   A consumer that displays the wrapper's `verify` block as a checkmark is
   laundering — this is the R30 verify-before-download lesson from the
   consumer side.
2. **Key provenance is the open seam.** The pilot's ephemeral key is honestly
   labeled (`key.ephemeral: true`), but an embedded public key establishes
   only *binding*, not *identity*. Standing identity requires a key the
   auditor already trusts out-of-band (key id registry, or the IETF/SCITT
   receipt-transparency lane pinned in STONE-SPEC §9). Until then a signed
   chain proves "one key signed this tip continuously", not "Casey signed it".
3. **The two gates are complementary and both are cheap.** Hash chain =
   content continuity. Staple = continuity was signed and not re-written.
   Auditing only one gate is the failure mode the laundering control exists
   to demonstrate.
4. **Total audit cost**: one dynamic `import`, two function calls, three
   one-line mutations. Sub-second. Receipt verification at consumer side is
   not a tooling problem anymore; it is a key-distribution problem.
